## 1. 现在的结构

### 1.1 分层

```
入口        命令行 app/agent/__main__.py      网页 app/api（RunManager、确认门）
              │                                  │
服务层      RagAgentService.query_result（一次请求的全部装配，约 220 行）
              │  会话与归档、长期记忆召回、hooks 装配、模型、工具注册表、
              │  选择执行模式（single / team / auto）、选择规划器、构造运行时、发布结果
              │
运行时      AgentRuntime._run：规划 → 逐步执行 → 失败就重新规划 → 最后一步的结果即答案
              │
  规划      Planner（独立一次模型调用，返回 {"steps": [...]}）  /  SingleStepPlanner（团队用，固定一步）
  执行      Executor.accept_plan → StepExecutor.execute → RoutingStepRunner（按能力选执行器）
              │
执行器      ToolCallingStepRunner（一步内：模型 ⇄ 工具，最多 4 轮、8 次）
            DelegatingTeamRunner（负责人循环 + delegate 工具，每个成员又是一个 ToolCallingStepRunner）
              │
模型        HookedModel → OpenAICompatibleToolCallingModel（外面还可能套 ContextManagedModel、
            PlanningModel、团队的 _Counted 和 _CompactingManager）
工具        SideEffectWatch → 只读过滤 → HookedToolRegistry → HookedTool → MCP 适配 → MCP 服务进程
状态        WorkingMemory（TaskState + Resources），ConversationMemory + ConversationArchive
横切        hooks（D-058～D-061）、RunMeter 计量和预算、ContextManager 上下文预算
```

### 1.2 一次普通问答实际发生了什么

以“解释某个函数在做什么”为例：

1. 服务层写入用户这一轮，准备对话历史并钉进任务状态；如果开了长期记忆，再召回一次。
2. `auto` 模式下先调用一次模型选执行方式；`single` 模式跳过。
3. 运行时把工具清单（名字和说明）钉进任务状态，进入规划。
4. **规划调用**：把任务状态整个序列化成 JSON 发给模型，拿回 1 到 8 个步骤。评测里绝大多数任务只有 1 步。
5. **执行第 1 步**：执行器把同一份任务状态再序列化一遍，作为用户消息；模型在步内调用工具，最多 4 轮、8 次。
6. 模型最后必须回一个 JSON 信封 `{"status", "content", "reason"}`，而且答案要转义后放在 `content` 这个字符串里。格式不对就进入格式修复。
7. 计划里没有剩余步骤，任务完成，最后一步的 `content` 就是答案。

调参集 11 题共 52 次模型调用，平均每题约 4.7 次，其中至少 1 次是规划。

## 2. 核心抽象：设计意图和实际用法

| 抽象 | 设计时想解决的事 | 现在实际的情况 |
|---|---|---|
| 计划（`PlanStep`） | 复杂任务先拆步，每步独立执行，失败可以重新规划 | 大多数任务只有 1 步；D-052、D-053 和规划提示里的几条规则都在劝模型“尽量只排一步” |
| 步骤隔离 | 每步上下文干净、可控 | 后一步看不到前一步读过的原文，只能看到它写下的结论，于是又要求“读取和分析放在同一步” |
| 目标修订（`goal_revision`、`update_goal`） | 任务进行中用户改目标 | 服务层从不调用 `update_goal`，生产路径上修订号一直是 0 |
| 约束（`constraints`、`add_constraint`） | 给任务附加限制 | 没有任何调用方，每次都发一个空数组 |
| 资源上下文（`select_context`） | 选中知识片段放进上下文 | 没有任何调用方，`resource_contexts` 一直为空 |
| 状态版本和执行令牌（`state_version`、`ExecutionToken`、`StaleExecutionError`） | 防止并发执行写错状态 | 每个任务只在一个锁里串行运行；这套检查分布在 `TaskState`、`WorkingMemory`、`StepExecutor`、`RoutingStepRunner` 和服务层 |
| 执行器注册表和路由（`RunnerRegistry`、`CapabilityRoutingPolicy`） | 一步可以交给不同执行器 | 只有两个执行器；团队模式靠“固定一步计划 + 指定能力”强行走到团队执行器 |
| 团队（`DelegatingTeamRunner`） | 多个成员协作 | 实际已经是“负责人循环 + `delegate` 工具”，只是被包在一个假的单步计划里 |

**结论**：规划—执行骨架里很大一部分是为“多步、可改目标、可并发”的任务设计的，而真实负载几乎都是“读一些东西，然后回答或改文件”。团队模式反而已经自然长成了单一循环加委派工具的样子。

## 3. 问题（按根因归类）

### 问题 1：控制流的基本单位是“计划步骤”，不是“模型循环”（根因，影响最大）

- **固定成本**：每个任务都先付一次规划调用，规划上下文 6 千到 2 万令牌，即使只有 1 步。
- **信息断层**：步骤之间只传结论，不传证据。模型要么在一步里塞进全部工作，要么在后一步重读文件。
- **规则在补结构的洞**：“读取和分析放在同一步”“问答类优先一步”“最后一步按目标规定的形式交付”（D-037）“步骤工具用完先收尾”（D-053），都是因为结构不合适才加上的。
- **团队模式被扭曲**：为了复用骨架，团队要用 `SingleStepPlanner` 生成一个固定步骤，再靠能力要求路由到团队执行器，步骤时限还要比团队时限多留 5 秒。
- **重新规划成本高**：一步失败后整个计划重排，又是一次完整规划调用；而副作用保护（D-032）又不允许在写入或运行之后重新规划，所以重新规划只在只读失败时有用。

### 问题 2：任务状态为没有出现的场景而设计

- `TaskState` 928 行，包含目标修订、计划修订、状态版本、约束、钉住内容、草稿区（中间结果、最近观察、问题、失败记录）。
- 第 2 节列出的几项在生产路径上从未使用，但每次请求都会被序列化进规划和步骤的上下文，占令牌，也让模型多读了一堆空字段和版本号。
- 防过期的检查分散在四五层，读代码时很难判断哪一层真正起作用。

### 问题 3：限额和时限分散在太多地方

现在一次运行同时受这些限制：执行次数 16、重新规划 2 次、每步工具 4 轮 8 次、单步时限 60 秒、规划时限 60 秒、团队时限、团队内部的委派次数和负责人轮数、`RunMeter` 的令牌和时间预算、对话令牌上限、人工确认等待（还要暂停前面几个时限）。

其中“每步 4 轮 8 次”最伤：读一个大一点的代码库很容易用完，于是要么拆步（回到问题 1），要么进入收尾逻辑（D-053）。人工确认那一步为了让等待不计入时限，不得不加了 `pausable_deadline`，就是因为时限有好几层。

### 问题 4：上下文策略和模型包装是临时拼起来的

- 包在模型外面的层有：`HookedModel`、`ContextManagedModel`（只给规划器）、`ContextManager.generate`（执行器自己调用）、`PlanningModel`、团队的 `_Counted` 和 `_CompactingManager`。哪一层负责什么、按什么顺序，要读多个文件才能弄清楚。
- `ContextManager` 一个类管四件事：对话历史准备、长期记忆片段、工具结果截断和转存、上下文溢出后重试。
- 旧工具结果的折叠（`model_view.compact_model_view`）只有团队成员在用，普通模式没有。

### 问题 5：结束协议靠 JSON 信封

- 每一步最后都要回 `{"status", "content", "reason"}`，最终答案要转义成字符串放进 `content`。
- 这带来了格式修复（D-031）、形状错误、`format` 失败类型，以及“答案本身是 JSON 时怎么办”的特殊处理。
- 用原生工具调用表达“完成”或“需要问用户”，或者干脆把纯文本回复当作完成，可以去掉大部分这类逻辑。

### 问题 6：服务层过胖

`RagAgentService.query_result` 一个函数约 220 行，同时负责：请求幂等和重放检查、会话加载、长期记忆召回、hooks 装配、模型和工具的生命周期、执行模式选择、只读收回、规划器和执行器的选择、运行时的构造或重新绑定、结果发布和异常时的收尾。加任何新能力都要改这里。

### 问题 7：重复发送的信息

- 运行时把工具清单（名字和说明）钉进任务状态，而同样的工具又作为原生工具定义发出，每次请求发两遍。
- 规划和每一步都把完整任务状态序列化一遍，内容大部分相同。

### 问题 8：遗留代码

这次核对到没有任何地方引用的模块：

- `app/agent/aiops/`（5 个文件）；
- `app/agent/mcp_demo/registry_client.py`、`time_client.py`；
- `app/services/vector_index_service.py`。

另外 `app/core/dependencies.py` 里写死了本地 Ollama 压缩器，只有命令行和一个测试在用；`app/agent/mcp_client.py` 和 `app/tools/mcp_client.py` 名字重复，需要确认职责。

## 4. 应当保留的设计

这些是这段时间验证过、和“规划还是循环”无关的部分，重构时要原样保留：

- **hooks**（D-058～D-061）：事件、观察型和拦截型 hook、审计、令牌上限、网页确认。目标结构里它反而更重要，因为限额和验收门槛都可以放进拦截型 hook。
- **副作用保护**（D-032）：写入或运行之后结果不确定时，不自动重放。
- **宿主权限**（D-015、D-029）：受保护路径、写根限制、沙盒执行，都在工具内部，hook 只能加严。
- **只读任务收回写入和运行工具**（D-027、D-028）。
- **对话归档和请求幂等**：先持久化输入再做外部调用，重放请求返回归档结果。
- **工具注册表和 MCP 接入**、`RunMeter` 计量、失败分类和中文说明（D-033）、缓存友好的请求开头（D-057）。
- **评测集**：调参集 11 题、留出集 13 题，是判断改动好坏的唯一依据。

## 5. 建议的目标结构

### 5.1 一句话

**以“智能体循环”为唯一的控制流：模型在一个循环里看消息、调用工具，直到给出答案。规划、团队、提问都变成循环里的工具或 hook，不再是外层的控制结构。**

### 5.2 组件

```
入口（命令行 / 网页）
   │
会话服务  SessionService：会话、归档、幂等、长期记忆召回、结果发布
   │
运行装配  RunAssembler：按请求选项组装 模型档案 + 工具集 + hooks + 上下文策略 + 预算
   │
智能体循环 AgentLoop
   │  messages ──▶ 上下文策略（截断旧工具结果、溢出重试）──▶ 模型
   │  模型回复：
   │    · 普通工具调用 → 经 hooks 和权限检查后执行，结果追加进消息
   │    · todo 工具     → 更新待办清单（可选，由模型自己维护）
   │    · delegate 工具 → 起一个子循环（独立上下文、受限工具），只交回摘要
   │    · ask_user 工具 → 任务阻塞，保存循环状态，等用户回答后继续
   │    · 纯文本回复    → 任务完成，这就是答案
   │
状态      RunState：消息记录、待办、问题、用量（取代 TaskState/WorkingMemory 的大部分）
横切      hooks、RunBudget（调用、令牌、时间、工具次数，一处计算）
```

### 5.3 各部分怎么对应现在的代码

| 现在 | 目标 | 说明 |
|---|---|---|
| `Planner` + 规划调用 | `todo` 工具，或复杂任务在循环第一轮先写计划 | 计划成为模型的工作笔记，不再决定控制流 |
| `StepExecutor`、`Executor`、路由、执行器注册表 | 删除 | 只有一种循环 |
| `ToolCallingStepRunner` | `AgentLoop` 的核心 | 去掉“单步”假设和步内 4 轮 8 次的限制，改由 `RunBudget` 统一限 |
| `DelegatingTeamRunner` | `delegate` 工具 | 负责人就是主循环；验收门槛（必须有通过的测试运行）变成拦截型 hook |
| JSON 信封 | 纯文本即完成；`ask_user` 表示阻塞；失败用文本说明 | 去掉大部分格式修复 |
| `TaskState` 的修订号、约束、资源上下文 | 删除 | 等真需要“任务中途改目标”时再加 |
| `ContextManager` + `model_view` + 各种模型包装 | 一个上下文策略，挂在循环调用模型前 | 普通模式也获得旧工具结果折叠 |
| 写死在代码里的模型差异 | 模型档案 | 地址、窗口、价格、支持的参数、能否缓存 |
| `query_result` | `SessionService` + `RunAssembler` | 服务层只管会话，装配单独成一层 |

### 5.4 这个结构对已知问题的效果（预期，需评测验证）

- 简单任务少一次规划调用，也不再重复序列化任务状态。
- 不再有步骤之间的信息断层，D-037、D-052、D-053 里的几条补丁规则可以删掉。
- 团队模式和普通模式共用一个循环，`team_v2.py` 大部分可删。
- 时限从多层减到“一次运行一个预算”，人工确认的暂停也只需要处理一处。
- 风险是一个循环里上下文会持续变长，所以上下文策略（旧结果折叠）必须同时做好。

## 6. 分阶段迁移

每个阶段都能单独评测、单独回退；只有前一阶段的评测不差，才进入下一阶段。

| 阶段 | 内容 | 判断标准 |
|---|---|---|
| 0 | 清理第 3 节问题 8 列出的遗留代码；去掉重复发送的工具清单 | 测试和调参集不回退 |
| 1 | 新增 `AgentLoop` 作为一个执行器，挂在现有运行时下面，用固定的一步计划进入（和团队模式现在的做法一样），只给普通模式加一个开关 | 调参集、留出集对比：通过数不降，令牌和调用次数下降 |
| 2 | 普通模式默认走循环；加 `todo` 和 `ask_user` 工具；结束改为纯文本；旧工具结果折叠移到循环里 | 同上，再加阻塞恢复的测试 |
| 3 | 团队模式改为 `delegate` 工具，验收门槛改为拦截型 hook；删除执行器注册表、路由和 `team_v2.py` 的大部分 | 团队评测不低于现在 |
| 4 | 精简任务状态，拆分服务层，加模型档案；删除规划—执行骨架 | 测试和两套评测不回退 |

阶段 1 是关键的试验点：它复用现有骨架，改动小，可以用评测直接回答“单一循环是不是更好”，答案不好就停在这里。

## 6.1 第 1 阶段试验结果（2026-11-07）

调参集各跑 1 次，和规划模式（加 hooks 后那次）对比：

| | 规划模式 | 单一循环 |
|---|---|---|
| 严格通过 | 11/11 | 11/11 |
| 模型调用 | 52 次 | 44 次 |
| 令牌 | 1,091,043 | 878,778（少 19%） |
| 用时 | 336 秒 | 308 秒 |

- 读资料后回答的 5 题，每题从 4～5 次调用、8.7 万～11 万令牌降到 2 次、约 4.1 万令牌。
- 修复代码的 3 题反而多用了：5～7 次调用、14.6 万～14.9 万令牌（规划模式 5～6 次、11 万～13.6 万）。原因还没查，可能是一个循环里消息一直变长，也可能是模型多调了 `todo`。
- 留出集各跑 1 次，对比规划模式（加 hooks 前那次）：

| | 规划模式 | 单一循环 |
|---|---|---|
| 严格通过 | 11/13 | 12/13 |
| 模型调用 | 67 次 | 57 次 |
| 令牌 | 1,282,560 | 1,321,752（多 3%） |
| 用时 | 467 秒 | 362 秒 |

- `call_chain_qa` 由失败变为通过；`side_effects_qa` 两种模式都错在 `mutates_arguments`。
- 令牌总数噪声很大：经中转站的请求有时另加约 1.5 万令牌，有时不加（例如 `role_perms_qa` 规划模式 4 次调用只用了 1.86 万令牌，循环 6 次用了 17.4 万）。调用次数和用时更可靠。
- 两套合计：规划 22/24，循环 23/24。

## 7. 风险

- **上下文变长**：长任务在一个循环里，消息会越来越多。要靠旧工具结果折叠和溢出重试，并用评测的令牌数盯住。
- **模型不守待办**：去掉强制规划后，较弱的模型在复杂任务上可能漏步骤。保留“复杂任务先写计划”作为后备。
- **测试大量改动**：现有 1581 项测试里，很多直接测 `TaskState`、`StepExecutor`、路由和团队内部。阶段 3、4 会删改大量测试，需要按阶段确认。
- **阻塞恢复**：循环被 `ask_user` 打断后要保存完整消息，进程重启后仍然不能恢复（和现在一样）。
- **评测样本小**：每题只跑一次，通过数的差别要结合令牌、调用次数一起看。
