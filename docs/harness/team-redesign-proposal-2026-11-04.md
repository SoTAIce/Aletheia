# 团队模式重新设计方案（2026-11-04，待用户决定）

本文只是方案，尚未实施。依据：当前代码（`app/agent/team/`）和本日 6 轮真实评测记录（[team-diagnosis](team-diagnosis-2026-11-04.md)、[team-recovery](team-recovery-2026-11-04.md)、[sandbox-live](sandbox-live-2026-11-04.md)）。

## 一、结论：是设计问题，不只是参数问题

过去 6 轮里，每修一处，就会暴露出下一处问题：参数修复次数、成员失败即全队失败、审查成员工具检查、未注册工具名、预算、上下文超窗、负责人不结束、每步都开团队。这些问题互相独立，但根源只有几个，都在结构层面。同一模型下，普通模式 2/2 通过（每项 5–6 次执行、100–160 秒），团队模式 0/2。

## 二、检查出的设计缺陷

| # | 缺陷 | 代码位置 | 实际后果 |
|---|---|---|---|
| 1 | **双层编排**：外层“计划—执行—重新计划”把任务拆成多步，每一步又启动一整个团队（负责人 + 执行成员 + 审查成员），负责人再自己编排一次 | `TeamStore.get` 以步骤为键；`agent_team_runner.py` 按步骤运行 | 小任务也要开 3–5 个团队；最后一轮两项都在 700 秒时被终止 |
| 2 | **成员是长寿命会话**：成员的会话跨多次返工持续累积，每次写文件的完整代码都留在历史里 | `TeamSession` 的 `revise` / `pause_at_boundary` | 32768 token 的窗口很快超出；只能靠“压缩视图”补救 |
| 3 | **负责人用一个通用 JSON 命令说话**：所有动作都塞进 `submit_result` 的 6 个字段（action、member_id、target_id、instruction、tools、expected_version），每次只能发一条 | `coordinator.py` 的 `COMMAND` 契约与 `_command` | 能力较弱的模型频繁出格式错误、调用不存在的工具；每个动作都要一次负责人模型调用 |
| 4 | **结束权交给模型，验收分三层**：宿主门槛（测试通过）+ 模型审查成员 + 负责人主动发 `finish` | `_execute` 的 `finish` 分支 | 门槛全部满足后，负责人仍然多次选择返工而不结束；审查成员只看截断的证据预览，判断价值有限 |
| 5 | **审查是强制的模型步骤**：没有审查通过就不能结束，而真正可靠的判定（沙盒测试通过）已经由宿主掌握 | `_finish_ready` 要求审查通过 | 增加模型调用和返工循环，没增加正确性 |
| 6 | **大量自制协议**：版本号、过期审查失效、暂停/修订、成员失败上限、格式修复的团队总额…… | `session.py` 448 行 + `coordinator.py` 480 行 | 每条协议都是新的失败点，修复是一路打补丁 |
| 7 | **任务类型不匹配**：评测任务是单文件编码，前后步骤强依赖，不能并行 | `bench/tasks` | 团队的主要优势（并行、隔离的上下文）用不上，只剩协调成本 |

关于“理论上团队应该比普通模式好”：业界的经验并不支持这个前提。多智能体在**可以并行、彼此独立的广度型任务**（如多方向资料调研）上明显更好；在**前后强依赖的编码任务**上，单个智能体保持完整上下文通常更可靠，多智能体的主要风险是上下文割裂和协调成本。对这类任务，团队合理的目标是“不比普通模式差，并多一道独立检查”，而不是一定更好。

## 三、可借鉴的成熟做法

| 来源 | 做法 | 对应本项目的缺陷 |
|---|---|---|
| Anthropic 多智能体调研系统、Claude Code 的子智能体 | 编排者—执行者模式：主智能体把子任务委派给**全新上下文**的子智能体，子智能体只交回精简结果；委派说明要写清目标、输出格式、可用工具和边界 | 2、3 |
| OpenAI Agents SDK 的“智能体作为工具”、LangGraph 的主管模式 | 委派、交接都是**普通的有类型工具调用**，不是自定义命令语言 | 3、6 |
| SWE-agent 等编码智能体、各类评测框架 | 以**可执行的检查**（测试通过）为主要验收标准，由宿主判定是否完成；模型审查只作补充 | 4、5 |
| Cognition《不要构建多智能体》 | 编码任务优先单线程、共享完整上下文；状态放在文件系统里，而不是消息历史里 | 1、2、7 |

## 四、方案：团队模式 V2（编排者—执行者，执行者即工具）

### 结构

```
用户目标
  └─ 负责人（一个普通的工具调用智能体，复用 ToolCallingStepRunner）
       工具：delegate(任务说明, 工具清单)  → 新建执行者，全新上下文，跑完返回摘要
             review(检查重点)             → 可选：只读审查者，全新上下文，返回意见
             （宿主）每次 delegate 结束后自动运行验收检查，把结果放进返回值
       结束：宿主门槛满足即自动完成；负责人也可以用普通最终回答结束（同样要过门槛）
```

### 关键变化

1. **团队负责整个任务，不再每步一个团队**：团队模式下外层计划只产生一步（或团队直接接管目标），负责人就是唯一的编排者。解决缺陷 1。
2. **执行者每次委派都是全新会话**：直接复用普通模式已经验证过的 `ToolCallingStepRunner`（2/2 通过），每次委派单独计预算；共享状态放在工作目录的文件里，返工就是新的委派，说明里写“读取现有文件，修正以下问题”。不再需要版本号、暂停/修订、视图压缩。解决缺陷 2、6。
3. **委派是普通工具调用**：`delegate` 只有两三个字段，宿主做校验（工具白名单、写入和执行工具只给执行者）。参数错误仍走已有的参数修复。解决缺陷 3。
4. **宿主决定是否完成**：开启沙盒时，最后一次写文件之后有通过的运行，就由宿主判定完成；模型审查改为可选（选项控制，默认关闭）。负责人不需要“记得”发结束命令。解决缺陷 4、5。
5. **委派返回精简结果**：执行者的最终回答 + 宿主附加的事实（写了哪些文件、最后一次运行的退出码和摘要），不回传完整工具历史。负责人上下文保持很小。
6. **保留的安全性质**：工具白名单、只读审查者、总预算（模型调用、工具调用、时间）、失败不自动重放、轨迹只记录宿主数据。这些作为 `delegate` 工具和运行器上的检查实现，沿用现有测试思路。
7. **并行留到后面**：先做顺序委派。将来只对只读调研类子任务开放并行委派（`asyncio.gather`），写文件的委派始终串行。

### 预期规模

新代码估计 250–350 行（一个负责人运行器 + `delegate` / `review` 工具 + 验收检查），复用普通模式执行器、参数修复、沙盒工具和轨迹。现有 V1（`app/agent/team/` 约 1300 行）在 V2 通过评测前保留不动，可以通过选项切换。
