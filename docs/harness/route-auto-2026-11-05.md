# 按任务动态选择执行模式（route-auto-001，决策 D-026）

日期：2026-11-05。来源：用户“先按如此写”（采用“规则 + 模型”方案的第一阶段）。

## 做了什么

- 新模块 `app/agent/route_selection.py`：
  - `allowed_modes(team_options)`：宿主规则层。没有团队选项（`team_unavailable`）、只读（`read_only`）、没有沙盒（`no_sandbox`）时只允许普通模式；允许写文件且开启沙盒时两种都允许（`code_delivery_with_sandbox`）。
  - `choose_mode(goal, team_options, model)`：规则只剩一种时直接采用；否则向模型发一次不带工具的 JSON 询问，回复必须是 `{"route": ..., "reason": ...}`，且模式在规则允许的范围内。出错、超时（20 秒）或格式不对一律退回普通模式；取消照常向上传递。任务文本最多发送 4000 字。
  - 每次决策记录 `Route decision: {...}`：模式、来源（`user`、`rule`、`model`、`fallback`）、规则名和异常类型链，不含模型原文；平时是 INFO，`ALETHEIA_TEAM_TRACE=1` 时是 WARNING。
- 服务 `RagAgentService`：
  - 接受 `execution_mode='auto'`；每个新任务在创建计划器之前选一次模式，选团队时才使用单步计划器、团队注册表和 `agent_team` 能力要求。
  - 被阻塞的任务恢复时沿用原来的选择；任务结束后清除记录。
  - 固定模式行为不变，只多记一条“用户指定”的决策。
- 命令行：`--execution-mode auto`；只有同时给了 `--write-root` 和 `--sandbox` 才会生成团队选项，否则规则直接定为普通模式。
- 评测器：`--modes` 支持 `auto`，团队相关参数（时限、独立验收）也传给 `auto`；结果行新增 `route`。
- 顺带修正：删除评测器里 V1 删除后遗留、已不起作用的 `--team-version` 参数；项目交接文档的调用链图更新为 V2 并加入路由选择。

## 没做什么

- 按步骤选择运行器（第二阶段）：需要团队能只接管某一步，并修改计划器输出格式（`planner.py` 有用户未提交的改动）。
- 路由准确率的真实评测：需要用户授权；评测任务也还需要补充只读问答类任务，才能检验“该选普通模式”的情况。

## 只读问答任务 billing_qa（用户 2026-11-05“可以补一个只读问答类任务”）

- 新任务 `bench/tasks/billing_qa`：阅读 `billing.py` 回答 5 个问题（常量、函数名、两次滞纳金计算、重试等待列表），最终答案只输出一个 JSON 对象；标准答案在隐藏的 `expected.json`，并用测试核对它与公开代码一致。
- 评分器 `answer_json`：每个键一项检查；严格评分要求整个答案就是一个 JSON 对象（允许代码围栏）；宽松评分（只作诊断）取答案里最后一个 JSON 对象。
- 评测器：`delivery: answer` 的任务在开启沙盒时仍提供写入和运行工具（这样 auto 才会真的询问模型），但使用原目标、不加“先测试”的提示、按最终答案评分；另加一项 `workspace_unchanged`，工作区有任何改动都算失败。
- 路由标注：`billing_qa` 应选普通模式，`parse_duration`、`fix_inventory` 应选团队；`auto` 结果行记录 `route_correct`，汇总里统计路由正确数和各模式次数。
- 只打印计划时不再因超过 `--max-runs` 而报错，只注明“真实运行会被拒绝”；真实运行仍然拒绝。

| billing_qa | 2 | 普通（模型） | 是 | 未通过：答案无法解析为 JSON | 31 秒 | |

### 结论

- **路由 6/6 正确**：都由模型判断（规则留下了两种模式），没有一次退回默认值。
- **parse_duration 3/3 严格通过**。第 1 次正好出现了执行者最终报告格式错误，团队仍然完成；这次的轨迹没有记录宿主是否保留了那个执行者的结果（报告中的门槛为未通过，说明它在测通之前就出错了）。
- **billing_qa 0/3，问题不在路由，而在普通模式的最终答案格式**：运行时把所有步骤的结果用空行拼成最终答案（`app/agent/runtime.py` 中 `"\n\n".join(results)`）。计划器把问答拆成多步时，最终答案前面是说明文字，最后才是 JSON，严格评分必然失败。当时的宽松评分只截取第一个 `{` 到最后一个 `}`，遇到多段内容也解析失败，所以看不出答案内容本身对不对。
- **只读约束未被遵守 1 次**：目标写明“不要修改或新建任何文件”，普通模式仍写了文件。
- 已改进诊断：宽松评分改为取答案中最后一个 JSON 对象；结果行新增 `answer_json_objects`（答案里的 JSON 对象个数）和 `answer_chars`（答案长度），都只是数字，不含原文。
- 未改：最终答案的拼接方式（会改变普通模式所有任务的输出，需要用户决定）。

## 对照：拼接全部步骤 vs 只取最后一步（用户 2026-11-05“先比较下只去最后一步结果的准确率”）

- 评测器新增对照评分（不改运行时）：`bench/graders.py` 的 `last_block()` 从答案末尾往前取最短的、能整体解析为一个 JSON 对象的若干段落（以空行分隔，允许代码围栏），近似“最终答案只取最后一步”。结果行新增 `last_step_checks_passed`、`last_step_all_passed`，汇总新增 `last_step_passed`。只记录数字。
- 近似的局限：如果最后一步本身是“说明 + 空行 + JSON”，这里也会算通过，所以结果是“只取最后一步”的上限。

### 结论

- **答案内容：拼接 0/6，只取最后一步 5/6**（第 1 次有一个值算错）。每次答案里有 3～4 个 JSON 对象，说明前面的步骤也输出了 JSON 片段。
- **只读约束：6 次里 4 次改动了工作区**（上一轮是 3 次里 1 次）。所以即使改成只取最后一步，完整严格通过也只有 1/6（第 3 次）。目前结果行不记录改了哪些文件，无法判断是写了笔记还是改了 `billing.py`。
- 路由 6/6 选普通模式，全部由模型判断。
- 未改：运行时的拼接方式、普通模式的写文件行为。

## 两项一起改（决策 D-027，用户 2026-11-05“两项一起改”）

- `app/agent/runtime.py`：普通模式的最终答案只取最后一个有效步骤的结果；前面步骤的结果仍在 `scratchpad.intermediate_results` 中。
- `app/agent/route_selection.py`：路由回复新增 `writes` 字段；`writes: false` 时 `ModeChoice.read_only` 为真，决策日志多一项 `"read_only": true`。新增 `read_only_registry()`，用同一批工具对象生成不含 `write_file`、`run_tests`、`run_python` 的注册表，原注册表不变。
- `app/services/rag_agent_service.py`：保存每个任务的完整 `ModeChoice`；只读任务交给运行时的是收回工具后的注册表，被阻塞任务恢复时沿用。
- 测试（`tests/test_route_selection.py` 新增 8 项）：模型标记只读、缺字段保留工具、矛盾或非法值退回、只读注册表只隐藏三个工具、服务对只读任务收回工具而写代码任务不变、两步计划的最终答案只取最后一步且前面结果仍保留。
- 验证：当前 tests 160 passed、12 skipped；init.ps1 PASS。历史回归 1021 passed，新增 1 项预期失败 `agent/test_runtime.py::test_failed_tool_replans_and_preserves_prior_valid_results`（它断言最终答案包含前面步骤的结果，正是本次改掉的行为；同一测试里“后续步骤能看到前面结果”的断言不受影响），其余 3 项已知失败和 4 个 V1 收集错误不变。

结论：

- **严格通过 3/6**（改之前 0/6）。完成的 5 次答案都是单个 JSON 对象，工作区都没有改动（改之前 6 次里 4 次改动）。6 次都被模型判为只读，路由全对。
