# 沙盒执行设计方案（草案，待用户审阅）

日期：2026-11-04。状态：**方案已获用户采纳（见决策 D-014），尚未实现**。第 12 节的问题已有答复：采用 Docker；第一版只支持 Python；接受默认限制；授权 Claude 拉取基础镜像并构建沙盒镜像。
对应增强路线的阶段二（受限写入）和阶段三（执行验证闭环）。

---

## 1. 为什么需要它

第一轮评测说明了问题（见 [阶段一记录](harness/capability-phase1-2026-11-04.md)）：

- 智能体现在只有只读工具（读文件、列目录、查时间），**不能写文件，也不能运行代码**。
- 它说“写好了”，只是自己读了一遍；团队模式的审查成员“批准”，也只是读文本。
- 结果：时长解析任务漏了一条规则，智能体自己发现不了；页面要重复输出两遍，也没有办法检查。

目标：让智能体能**写代码 → 运行测试 → 看结果 → 修改**，直到测试通过，再交付。

---

## 2. 先搞清楚几个概念

| 名词 | 通俗解释 |
| --- | --- |
| 沙盒 | 一个隔离出来的小环境，里面的程序随便折腾，也碰不到外面的东西 |
| 镜像 | 环境的“模板”，比如“装好 Python 3.13 和 pytest 的精简 Linux”。做一次，可以反复使用 |
| 容器 | 用镜像临时启动的一份运行环境。用完即删，下次再起一份新的 |
| 挂载 | 把电脑上的某个目录“借给”容器使用。只借一个临时目录，容器就只能看到这个目录 |
| 宿主 | 指我们的程序（Aletheia）本身。限制由宿主设定，模型改不了 |

**关键原则：沙盒不是智能体自己加的。** 宿主事先搭好沙盒，只交给智能体两三个固定用途的工具（例如“运行测试”）。限制参数写死在宿主代码里，模型既看不到开关，也申请不到更多权限。这和现有的决策第三条一致：能力只能来自可信来源。

---

## 3. 方案选择

| 方案 | 你电脑上的情况 | 隔离强度 | 结论 |
| --- | --- | --- | --- |
| Docker 容器 | 已安装 Docker Desktop，引擎当前未启动 | 强：断网、限内存、限处理器、限进程数，都有现成参数 | **推荐** |
| WSL 中的 Ubuntu 22.04 | 已安装 | 中：默认能访问 Windows 磁盘，要额外加固 | 备选 |
| 本机直接起子进程 | 现在的评分器就这么做 | 弱：只能防误伤，挡不住恶意代码 | 不给智能体用 |
| Windows 沙盒 | 未启用 | 强，但很难用程序自动控制 | 不采用 |

下文都以 Docker 为准。

## 4. 总体结构

```
用户目标
   │
   ▼
Aletheia 宿主（规划 / 执行 / 团队协调）
   │  只交给模型这几个工具：
   │   read_file / list_directory         只读，范围是任务根目录
   │   write_file                         只写，范围是本任务的工作目录
   │   run_tests / run_python             在沙盒中运行，宿主定死限制
   ▼
沙盒执行器（新增，位于宿主进程内）
   │  每次调用：启动一个全新容器 → 执行 → 收集结果 → 删除容器
   ▼
Docker 容器
   - 只挂载本任务的工作目录 → 容器内 /work
   - 断网，只读根文件系统，非 root 用户
   - 限时、限内存、限处理器、限进程数
```

**每个任务一个独立工作目录**：放在系统临时目录下，例如 `%TEMP%\aletheia-work-<随机名>`。任务结束后整体删除。项目源码、`.env` 和用户文件都**不会**挂进容器。

## 5. 阶段二：受限写入

> 实施状态（2026-11-04，sandbox-step1-001）：第 2、3 项已实现（见决策 D-015）；第 1 项暂由评测运行器创建临时根目录代替；第 4 项在评测集的 `--write` 模式中实现。

现状：文件工具服务（`app/tools/filesystem/server.py`）已经支持 `write_file`，只是要传 `--write-root` 才会开启。它会拒绝绝对路径、`..` 越界、链接和超大文件，默认不允许覆盖已有文件。

需要补的部分：

1. **工作目录由宿主创建**：命令行增加类似 `--workspace auto` 的选项，宿主在临时目录里新建工作目录，同时作为读根和写根，并把任务公开文件复制进去。不让模型指定路径。
2. **团队模式白名单**：默认白名单里没有 `write_file`。只有开启工作目录时，宿主才把 `write_file` 和运行工具加入白名单。默认仍然只读，不改变现有行为。
3. **按角色分权**：协调器在创建成员时已区分执行成员和审查成员（`app/agent/team/coordinator.py` 约第 205–208 行）。新增宿主规则：**写入和运行工具只能授予执行成员**；审查成员只能读文件、看运行结果。负责人如果给审查成员申请这些工具，命令直接被拒绝。
4. **交付方式改变**：最终答案只交“文件路径加摘要”，不再把整份代码塞进 JSON。这样也解决了第一轮暴露的交付格式问题（答案夹带说明、重复输出）。评测运行器从工作目录里读文件来评分。

## 6. 阶段三：沙盒运行工具

### 6.1 给模型的工具（只开放固定用途，不开放任意命令行）

| 工具 | 参数 | 作用 |
| --- | --- | --- |
| `run_tests` | `path`（工作目录内的测试文件或目录，可选） | 在容器里执行 `python -m pytest -q`，返回通过/失败数和截断后的输出 |
| `run_python` | `path`（工作目录内的 .py 文件），`args`（最多若干个字符串） | 执行一个脚本，返回退出码和截断后的输出 |

不提供“执行任意命令”的工具，原因是越通用越难约束，而且第一阶段用不到。

### 6.2 每次运行的容器限制（宿主写死）

| 限制 | Docker 参数（示意） | 防什么 |
| --- | --- | --- |
| 断网 | `--network none` | 下载东西、外传数据 |
| 只挂载工作目录 | `-v <工作目录>:/work` `-w /work` | 读写项目源码、`.env`、个人文件 |
| 根文件系统只读 | `--read-only --tmpfs /tmp:size=64m` | 改坏环境本身 |
| 非 root 用户 | `--user 1000:1000` | 提权 |
| 去掉特权 | `--cap-drop ALL --security-opt no-new-privileges` | 利用内核能力逃逸 |
| 内存 | `--memory 512m --memory-swap 512m` | 吃光内存 |
| 处理器 | `--cpus 1` | 占满处理器 |
| 进程数 | `--pids-limit 128` | 无限创建进程（进程炸弹） |
| 时间 | 宿主计时 30 秒，超时强制删除容器 | 死循环 |
| 环境变量 | 不传任何宿主环境变量 | 泄露接口密钥 |
| 输出 | 只回传前 20,000 个字符 | 撑爆模型上下文 |
| 用后即删 | `--rm`，任务结束再删工作目录 | 残留 |

### 6.3 镜像

在仓库中新增 `deploy/sandbox/Dockerfile`：基于官方 `python:3.13-slim`，只额外安装 `pytest`，建一个普通用户。构建一次后在本地使用，名字如 `aletheia-sandbox:py313`。

- 构建镜像需要**从网上下载基础镜像**（约几十兆）。按项目规则，我不能自动下载，需要你明确同意或自己执行构建命令。
- 镜像构建好之后，运行时完全断网，不再下载任何东西。

### 6.4 智能体的工作循环

1. 读需求 → 写代码到工作目录。
2. 自己写测试（或运行任务自带的公开测试）→ `run_tests`。
3. 看失败信息 → 改代码 → 再运行。
4. 测试通过 → 交付文件路径和测试结果摘要。

团队模式：执行成员负责第 1–3 步；**审查成员必须依据最近一次运行结果来批准**。没有运行记录，或运行结果是失败，都不能批准。这一条由宿主检查，不靠提示词。

### 6.5 预算

- 每个步骤最多运行若干次（例如 10 次），计入现有工具调用预算。
- 运行时间计入任务总时长。团队模式默认总时长是 180 秒，跑代码可能不够。可以给代码类任务单独传更长的时长，但**不改默认值**。

## 7. 前端页面怎么测

Python 代码可以直接用 pytest。网页的交互（点击、localStorage）需要浏览器，有两种做法：

| 做法 | 优点 | 缺点 |
| --- | --- | --- |
| 镜像里装无头浏览器（Playwright + Chromium） | 最接近真实浏览器 | 镜像会增加约几百兆，构建时下载量大 |
| 镜像里装 Node.js + jsdom（模拟浏览器环境） | 小很多 | 不是真实浏览器，样式和布局测不了 |

建议第一版先只支持 Python。前端暂时继续用“交付后由评测工具在外部检查”，等 Python 闭环验证有效后再决定。

## 8. 怎么证明沙盒真的安全（先测沙盒，再交给智能体）

> 实施状态（2026-11-04，sandbox-step2-001）：镜像已构建，执行器已实现（决策 D-016）。下表 9 项加上“非 root 用户”和 pytest 运行，共 10 个真实容器测试全部通过：断网（Network is unreachable）、宿主文件不可见、只有 /work 和 /tmp 可写且 /tmp 不可执行、宿主环境变量不传入、死循环超时并删除容器、1GB 分配被内存限制终止（退出码 137）、进程数停在 127、10MB 输出截断到 20,000 字符、没有残留容器。

在把运行工具开放给模型之前，先用一组“故意搞破坏”的脚本测试沙盒，每一项都必须被挡住：

| 测试 | 预期 |
| --- | --- |
| 访问网络（连外网地址） | 失败 |
| 读取工作目录以外的文件（如宿主项目路径） | 看不到 |
| 往 `/work` 以外写文件 | 失败（根目录只读） |
| 读取环境变量里的密钥 | 不存在 |
| 死循环 | 30 秒后被终止，返回超时 |
| 申请 1GB 内存 | 被终止，返回内存超限 |
| 进程炸弹 | 被进程数上限挡住 |
| 输出 1MB 文字 | 只回传截断后的部分 |
| 结束后检查残留 | 没有遗留容器和工作目录 |

测试分两层：

- **确定性测试**：用假的执行器，检查宿主生成的 Docker 参数、超时处理、输出截断、权限分配是否正确。不需要 Docker，可以放进 `tests/`，由 init 运行。
- **集成测试**：需要 Docker 引擎在运行，执行上表里的破坏脚本。引擎没开时自动跳过，并在报告里写明“未验证”。

## 9. 失败时怎么处理

| 情况 | 处理 |
| --- | --- |
| Docker 引擎没开 | 不开放运行工具，智能体仍可读写；报告写明“未启用运行环境” |
| 镜像不存在 | 同上，并提示构建命令。不自动下载 |
| 单次运行超时 / 超内存 | 作为普通工具结果返回给模型（例如“超时”），由模型修改代码，不算整个任务失败 |
| 运行次数用完 | 不再提供运行工具，要求模型根据已有结果交付或报告失败 |
| 删除容器或目录失败 | 记录下来，在交接文档里列出，等人工处理 |

## 10. 剩余风险（要事先知道）

1. **Docker 不是绝对安全**：容器和宿主共用内核（在 Windows 上是 WSL2 虚拟机的内核）。对“写错代码”和一般恶意代码，它足够；但不能防高级的内核漏洞利用。如果以后要运行来源不明的代码，需要更强的隔离，比如 gVisor 或独立虚拟机。
2. **工作目录在宿主磁盘上**：容器能写这个目录。所以宿主读取结果时，要把里面的内容当作不可信数据（例如不能跟随其中的链接）。
3. **Windows 路径挂载**：Docker Desktop 通过 WSL2 挂载 Windows 目录，速度较慢，换行符也可能不同。需要在集成测试中确认。
4. **评测分数会变化**：有了运行能力后，模型调用和耗时都会增加，和第一轮的数字不能直接比较，需要重新跑同一批任务做对照。
