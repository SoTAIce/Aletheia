# 单一循环按需委派（修改方案）

日期：2026-11-10。状态：**已实现并评测，未提交；默认保持关闭**（方案 loop-delegate-plan-001，实现 loop-delegate-001，见第 10、11 节）。
来源：用户 2026-11-10“团队模式是不是该自动判断是否委托团队”“多参考 Claude Code 的实现，写一版方案，触发时机确实需要好好把握，不然会浪费很多 token”。依据是当前代码（`8ad053a`）、[第 3 阶段方案](stage3_team_delegate_plan.md) 的评测、Claude Code 的子智能体文档（第 2 节）。

## 1. 要解决的问题

现在要不要用团队，是在任务开始前由 `route_selection` 一次决定的（D-026）：

- 路由只看到目标文字，没读过任何文件，就要决定整件任务交不交团队；
- 只能全有或全无：团队负责人一个文件都不碰，单一循环又完全不能派活；
- 单一循环做到一半发现活太大，没有办法把一块派出去；
- `auto` 下每个新任务都先付一次路由调用。

架构梳理第 5 节的目标结构本来就是“主循环里有 `delegate` 工具”，第 3 阶段已让团队负责人变成挂了 `delegate` 的单一循环，但普通单一循环还没有它。本方案给普通单一循环加上**按需委派**：由模型在干活过程中判断，宿主用规则和预算兜底。

## 2. Claude Code 怎么做（参考）

据 [官方子智能体文档](https://code.claude.com/docs/en/sub-agents.md) 和它的工具说明：

| 方面 | Claude Code | 本方案取舍 |
|---|---|---|
| 谁决定委派 | 主智能体调用 `Agent`（原名 `Task`）工具；依据是各子智能体的 `description`、当前任务和上下文；用户也可以点名 | 同：主循环调用 `delegate` |
| 子智能体类型 | 内置 `Explore`（只读、快、只交回结论，可指定 `quick`/`medium`/`very thorough`）、`Plan`（只读调研）、`general-purpose`（全部工具） | 第一版只做只读的 `explore`；能写文件的 `worker` 留到第 8 节 |
| 上下文 | 全新上下文，看不到主对话和已读文件，只靠委派说明；只有最后的摘要回到主对话 | 同；成员的 `active_goal` 换成委派说明，不带对话历史（团队模式现在会带完整目标，见 4.3） |
| 嵌套 | 默认最多往下 3 层，可设为 1 关掉 | 固定 1 层：成员没有 `delegate` |
| 工具 | `tools` 白名单、`disallowedTools` 黑名单；子智能体永远不能向用户提问 | 同：只给只读工具，不给 `ask_user` |
| 花费 | 每个子智能体各自花令牌；非分叉的子智能体要从头收集上下文，增加延迟；简单任务可用便宜模型 | 本项目每次请求固定约 2 万令牌开销（D-063），一次委派至少多 2～3 次请求，所以门槛要比 Claude Code 更严 |
| 不该用的情况 | 需要来回迭代的任务；多个阶段共享大量上下文（规划、实现、测试）；快速、有针对性的小改动；在意延迟 | 写进工具说明（4.2） |

Claude Code 工具说明里另有几条做法也照搬：委派说明要自成一体并写明要交回什么；读一个已知路径的文件、在两三个文件里找东西时直接用读取工具，不要委派；子智能体的结果可以信任，不要再自己重查一遍；互相独立的几块可以在同一轮里一起派出去。

## 3. 目标行为

```
单一循环（主循环）
  工具：工作区工具 + todo + ask_user + delegate（仅在启用时）
  delegate(task, thoroughness)
    → 宿主检查次数、预算、轮次门槛
    → 起一个只读成员子循环：新上下文、active_goal = task、只读工具、无 ask_user、无 delegate
    → 交回：成员的纯文本结论 + 宿主证据（读过哪些文件、调用次数）
  主循环继续干活，自己写文件、自己回答
```

- 完成方式不变：主循环回纯文本即结束；单一循环没有 `PassingRunGate`，委派不改变这一点。
- 团队模式（`--execution-mode team`）和 `auto` 路由**这次都不改**，等第 7 节评测之后再定。

## 4. 触发时机（本方案的重点）

触发靠两层：宿主规则先把明显不该委派的情况挡掉，工具说明再告诉模型什么时候值得用。宿主规则模型不能绕过。

### 4.1 宿主规则（确定性，写在代码里）

| 规则 | 默认值 | 理由 |
|---|---|---|
| 默认关闭，启动参数 `--delegate`（命令行、网页后端、评测）打开 | 关 | 先评测再决定是否默认开启 |
| 只在单一循环（`--single-runner loop`）里提供；规划模式和团队模式不受影响 | — | 规划模式的步骤预算太小（4 轮 8 次），委派会挤占它 |
| 每个任务最多委派次数 | 2 | 一次委派按 3 次请求算约 6 万令牌，2 次已接近一道普通题的全部花费 |
| **第 1 轮不提供 `delegate`**：主循环至少自己调用过一轮工具后，才把它加进工具列表 | 开 | 路由的毛病就是没读文件就决定；先自己看一眼，才知道任务大不大。也能挡住“一上来就把整件事派出去” |
| 主循环剩余工具预算不足时不再提供（已用轮数 ≥ 上限的 75%） | 开 | 快到上限时委派只会让收尾更乱 |
| 成员预算 | 8 轮、16 次工具调用、120 秒 | 比团队成员（12/24）小，只读调研够用 |
| `thoroughness` 只能是 `quick` / `medium` / `thorough`，分别对应成员 4 / 8 / 12 轮 | `medium` | 仿 Explore；让模型为小调研选小预算 |
| 同一轮里多个 `delegate` 调用依次执行，计入次数 | — | 第一版不做并行，避免同时开多个沙盒或 MCP 调用 |
| 委派说明长度上限 | 4000 字符 | 防止把整段上下文塞进说明 |

被宿主规则拒绝时，`delegate` 返回一句宿主说明（例如“已用完 2 次委派，请自己继续”），不计入次数，不起成员。

### 4.2 工具说明（给模型看，参照 Claude Code）

`delegate` 的说明大意如下（实现时用英文，和其他工具说明一致）：

- **用途**：起一个只读的调研成员，它从零开始、看不到你的对话，读完文件后只交回结论。用来把“要翻很多文件、但你只需要结论”的调研挪出你的上下文。
- **值得用**：要在很多文件或很深的目录里找东西，而且你不知道该看哪几个文件；要弄清一个跨多个模块的调用链或数据流，中间读到的内容你之后用不上；有两三块互相独立的调研，每块都要读不少文件。
- **不要用**：
  - 已知文件路径，直接 `read_file`；
  - 在两三个文件里找东西，或者三次以内的工具调用能做完的事；
  - 你已经读过相关文件（成员要从头再读一遍，更贵）；
  - 需要边看边改、来回迭代的工作；
  - 把整个任务交出去，或者让成员替你复查你刚做完的事；
  - 只是为了“更稳妥”。
- **怎么写说明**：自成一体，写清要查什么、在哪儿查、交回什么（格式和长度，例如“列出调用 X 的函数和文件路径，不超过 20 行”）；选 `thoroughness`。
- **结果**：成员的结论可以直接用，不要再把它读过的文件自己重读一遍；要改文件、跑测试，你自己来。

单一循环的系统提示加一句：“`delegate` 只用于大范围调研；大多数任务不需要它。”

### 4.3 成员的上下文

- `active_goal` 换成委派说明；不带对话历史、长期记忆和固定上下文（`pinned_contexts`），只保留宿主规则需要的字段。这和 Claude Code 一致，也防止成员读到完整目标后去做整件事。
- 系统提示用现在团队成员的说明加只读要求，结尾要求“按说明要求的形式交回结论”。
- 团队模式的成员这次不改（仍带完整上下文），避免影响第 3 阶段已验证的结果。

## 6. 测试

全部用替身模型：

- 不开 `--delegate` 时单一循环的工具列表、提示和消息与现在逐字相同；
- 第 1 轮工具列表里没有 `delegate`，调用过一轮工具后才有；剩余预算不足时又消失；
- 次数上限、说明长度上限、非法 `thoroughness` 的宿主回复，且都不起成员；
- 成员：`active_goal` 是委派说明、没有对话历史、只有只读工具、没有 `ask_user` 和 `delegate`、预算随 `thoroughness` 变化；
- 成员出错时宿主报告只有异常类型；成员调用在 `member` 区间里、计入同一个用量计量；
- 规划模式、团队模式启用 `--delegate` 时不出现 `delegate`；
- 评测报告的 `delegations`、`delegate_calls` 计数正确。

## 7. 评测（需要授权）

触发时机好不好，只能用真实模型看。分两部分：

1. **不该委派的题不委派**：调参集 11 题，单一循环开 `--delegate` 跑 1 次，和 3b 的单一循环（10/11，28 次调用，606,738 令牌）比较。现有题目都很小，**理想结果是委派次数接近 0**。判断标准：通过数不低于 10/11，总令牌不超过 3b 的 1.1 倍，委派总次数不超过 2。
2. **该委派的题会委派**：现有评测集没有“大范围调研”类的题，建议新增 2 道探针题（新划分 `probe`，不并入调参集和留出集，见第 9 节第 3 问）：例如在一个有几十个文件的仓库里追一条调用链、汇总所有配置项的读取位置。开和不开 `--delegate` 各跑 1 次，看是否委派、主循环的提示令牌是否下降、答案是否仍正确。

两部分都满足，再讨论是否默认开启、是否用它替代 `auto` 路由和团队模式。

## 8. 以后可能做的（这次不做）

- **能写文件的成员（`worker`）**：要处理成员写入后的完成条件、与主循环同时改同一文件的冲突，代价和风险都更大；等只读版本的评测说明触发时机可控后再定。
- **并行委派**：同一轮的多个 `delegate` 同时跑。
- **成员用更便宜的模型**：Claude Code 让 Explore 和简单子任务用小模型降成本；本项目目前只有一个模型档案，需要先有模型档案（第 4 阶段）。
- **续问成员**：Claude Code 可以给已结束的子智能体发消息继续；本方案的成员一次性。
- **替代 `auto` 路由和团队模式**：看第 7 节结果再决定。

## 11. 评测（2026-11-11，用户“跑评测”）

真实模型，每题 1 次，参数与 3b 单一循环相同（只交答案、不开沙盒）。输出在 `output/`（被 git 忽略）：`bench-tune-loop-delegate.json`、`bench-probe-delegate.json`、`bench-probe-plain.json`，以及对应的 `traces-*` 目录。

**调参集，单一循环开 `--delegate`**（对照 3b 单一循环 `bench-tune-loop-3b.json`）

| | 开委派 | 3b |
|---|---|---|
| 通过 | 10/11 | 10/11 |
| 总令牌 | 511,221（0.84 倍） | 606,738 |
| 模型调用 | 25 | 28 |
| 委派（实际起成员 / 请求） | 0 / 0 | — |

第 7 节第 1 部分的三条标准都满足。各题多出约 300 到 700 个令牌，这是工具说明本身的开销。`config_merge_qa` 错了 `top_keys`：这次只调了 2 次模型就作答，3b 调了 5 次答对了；3a 时同一项也错过，判断为模型波动。`todo_html` 在 3b 没过，这次过了。

**探针题，开和不开各 1 次**

| 题 | 开委派 | 不开 |
|---|---|---|
| `probe_config_keys` | 6/6 通过；委派 2 次（都选 `thorough`），共 36 次调用，其中成员 25 次；897,740 令牌，235 秒 | 6/6 通过；5 次调用，145,401 令牌，41 秒 |
| `probe_event_flow` | 6/6 通过；没有委派；8 次调用，208,696 令牌 | 6/6 通过；9 次调用，249,770 令牌 |

结论：

1. **该委派的题，其实不需要委派。** 两道探针题不开委派也都答对了，而且很便宜。主循环用 `search_files` 在整个目录里一次搜出所有 `settings.get`，不用逐个读文件。“文件多”不等于“需要调研成员”：有全文搜索时，几十个文件的汇总只要几次调用。
2. **真委派了，代价很大。** 在 `probe_config_keys` 上，令牌是不开时的 6.2 倍，耗时是 5.8 倍。原因有三：
   - 两个成员都选了 `thorough`；
   - 成员大多每轮只读一个文件，各用了 12 轮左右；
   - 主循环拿到结论后又自己读了 7 个文件，没有照说明“信任结论”。
   每次请求还要固定付约 2 万令牌（D-063），所以每多一次成员调用都很贵。
3. **不该委派时，宿主规则和工具说明管用。** 调参集 11 题一次都没有请求委派。

建议：
- 保持默认关闭；
- 不用它替代 `auto` 路由或团队模式；
- 第 8 节的扩展（能写文件的成员、并行委派）先不做。

如果以后还想推进，先要找到不开委派就做不好的题：例如单次搜索找不到、必须沿多层间接调用逐个读的调研。在那之前改触发规则，没有依据。可以先做的小改动有三个：把 `thorough` 限制为每任务一次或去掉；让成员每轮并行读多个文件；结论里列出的文件不再让主循环重读。但都要有新题证明需要，才值得改。
