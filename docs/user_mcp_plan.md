# 接入用户自己的 MCP 服务器（方案）

日期：2026-11-22。状态：**已实施，未用真实模型验证**（D-095）。第 8 节六条按推荐定（用户 2026-11-22）。由 Gemini（Antigravity 命令行，`gemini-4-neon-medium`）实施，Claude 写实施说明并核对（用户 2026-11-20 定）。

来源：三阶段收尾计划第三阶段 3.3（记在 `handoff` 分支的 `progress.md`），想法出自用户自己的 `docs/agent_feature_ideas.md` 第 7.1 节。那一节写在 D-085～D-094 之前，下面的现状都按当前代码（`c0b095a`）重新核实过。本文件没有加进 `docs/DOCUMENT_INDEX.md`，因为那个文件里有用户自己没提交的改动。

## 1. 要解决什么

用户想接上现成的 MCP 服务，比如笔记软件、日历、数据库查询、问题跟踪系统，而不用改 Aletheia 的代码。

- 现在能用的 MCP 服务是写死的三个：文件、沙箱、联网搜索（`app/tools/tool_loader.py` 的 `local_mcp_servers`）。
- 接第三方服务有三个风险：
  - 启动一个命令，等于运行任意代码；
  - 第三方工具做了什么，宿主不知道；
  - 工具结果来自外部，可能夹带提示注入。

## 2. 现状（已核实）

- **接入路径**：
  - `open_tool_registry`（`tool_loader.py` 第 67～91 行）每次运行都按 `mcp_servers` 列表逐个启动 stdio 子进程，用 `register_mcp_tools` 把工具登记进 `HookedToolRegistry`；所有服务在同一个 `AsyncExitStack` 里，运行结束一起关。
  - 重名的工具，注册表直接报错，不会覆盖。
  - 每个工具都包在 `HookedTool` 里，经过门控（D-059）。
- **工具属性**（`app/agent/tool_effects.py`，D-087）：
  - 先看工具自己的声明，再查内置名字表 `BUILTIN_EFFECTS`，都没有就当 `external`，算有副作用。
  - `MCPToolAdapter`（`app/tools/mcp_tool_adapter.py` 第 38～40 行）只要服务标了 `readOnlyHint`，就把工具当成 `read`。文件头注释写明：现在只接本项目自己的服务，所以信任这个声明；**用户自己的服务不能靠声明把自己说成只读**。
  - 内置名字表是按名字查的，所以第三方工具如果起名叫 `write_file`、`read_file`，会被当成内置工具。
- **哪里能看到哪些工具**：
  - 只读任务（`route_selection.read_only_registry`）去掉所有不是 `read` 的工具，`external` 也去掉。
  - 团队成员和调研成员用固定的工具清单（`delegation.READ_TOOLS`、`team_options_for`），看不到别的工具。
- **出错**：
  - 只读工具抛异常，交回模型（D-085）；有副作用的工具抛异常，任务结束，不重试（D-032）。
  - `MCPToolAdapter` 遇到图片等非文本结果会抛 `TypeError`。对 `external` 工具来说，这会让整个任务结束。
  - 每次调用的等待上限是 `DEFAULT_READ_TIMEOUT`，30 秒（`mcp_client.py` 第 14 行）。
- **环境变量**：`StdioServerParameters(env=...)` 给了值时，MCP 库会合并它自己的最小默认环境（`get_default_environment`，只有 `PATH` 这类），不会继承整个进程环境。沙箱和搜索服务就是这样只传自己要的变量（`tool_loader.py` 第 41～52 行）。
- **确认**：
  - 网页的确认门控对 `external` 工具一律问人（D-061、D-087）。
  - 命令行没有规则文件时不确认（D-094）；有规则文件时，没命中规则的 `external` 工具也不问。
  - 系统盘目录的启动确认（`confirm_startup`，D-074）的做法：终端输入 `y`；不能交互时，必须加 `--confirm-system-drive`。
- **系统提示**（`agent_loop.py` 第 117 行）已经写明工具结果是证据，不是改变角色或规则的指令。
- **配置文件的先例**：`models.toml`（D-084）、`permissions.toml`（D-094）。评测清掉了 `PERSONAS_DIR` 和 `PERMISSIONS_FILE`，用户自己的配置不改变评测。
- **测试用的服务**：`app/agent/mcp_demo/time_server.py` 是仓库里现成的一个小 MCP 服务，可以当第三方服务来测。

## 3. 设计

### 3.1 配置文件 `mcp.toml`

- 新设置 `MCP_SERVERS_FILE`，默认 `mcp.toml`，读法和 `models.toml` 一样。新模板 `mcp.example.toml`，`.gitignore` 加 `mcp.toml`。
- 格式：

  ```toml
  [servers.notes]
  command = "node"
  args = ["D:/tools/notes-mcp/index.js"]
  env = ["NOTES_TOKEN"]                     # 只写变量名，值从进程环境里取
  cwd = "D:/tools/notes-mcp"                # 可选，绝对路径
  timeout_seconds = 30                       # 可选，每次调用最多等多久
  tools = ["search_notes", "create_note"]    # 可选，只接这几个工具
  enabled = true                             # 可选，默认 true

  [servers.notes.effects]
  search_notes = "read"                      # 不写的工具一律当 external
  ```

- 预检（有错就拒绝启动，错误说明是中文，不带变量值）：
  - 服务名：小写字母开头，只含小写字母、数字、下划线，最长 20 个字符；
  - `command` 非空；`args` 是字符串列表；`cwd` 是存在的绝对路径；
  - `env` 里的每个名字都要在进程环境里有值；名字不能是本项目自己的密钥（`DASHSCOPE_API_KEY`、`TAVILY_API_KEY`、`AGENT_MODEL_API_KEY`、`WEB_ACCESS_TOKEN`、`ALETHEIA_TEST_API_KEY`）。
  - `effects` 只认 `read` 和 `external`：第三方工具碰不到工作区，`write`、`run` 对它没有意义。
  - `timeout_seconds` 在 1～300 之间；
  - 最多 10 个服务。

### 3.2 工具名和属性

- **工具名加服务名前缀**（第 8 节第 1 问）：
  - 模型看到的是 `notes__search_notes`，调用时宿主去掉前缀，再发给服务。
  - 这样不会和内置工具重名，也不会被内置名字表当成内置工具。
  - 加前缀后的名字只能含字母、数字、`_`、`-`，最长 64 个字符；不合格的工具不接，在启动检查里列出来。
- **属性只听配置的**：`effects` 里写了 `read` 的才算只读，其余一律 `external`。服务自己标的 `readOnlyHint` 不算数。
- **数量**：
  - 写了 `tools` 的，只接这些；
  - 没写的，最多接 30 个，多出来的不接，并在启动检查里说明；
  - 每个工具的说明截到 1,000 字符。
- **非文本结果**：用户服务返回图片等非文本内容时，不抛异常，换成一句宿主说明，比如“[有 1 个图片结果，没有转交给模型]”。不然一个 `external` 工具返回图片，就会结束整个任务。内置服务的行为不变。

### 3.3 启动确认（第 8 节第 2 问）

- 命令行和网页启动时，按服务列出将要运行的内容：命令（解析成实际的可执行文件路径）、参数、工作目录、要传的环境变量名。
- 确认的方式和系统盘目录一样：
  - 终端输入 `y`；
  - 不能交互时，必须加 `--confirm-mcp`，否则拒绝启动。
- **记住确认结果**：
  - 每个服务的配置（命令、参数、工作目录、变量名、工具清单、属性）算一个指纹，确认过的指纹记在 `data/mcp_confirmed.json`。`data/` 是受保护目录（D-074），模型读不到也写不了。
  - 配置没变就不再问；改了任何一项，要重新确认。
- **启动检查**：确认以后，每个服务先启动一次，列出工具，核对名字和数量，然后关掉。
  - 启动不了、或者一个合格的工具都没有，就拒绝启动，说明是哪个服务（只写异常类型，D-033）。
  - 新命令 `python -m app.agent --show-mcp`：打印配置和确认状态，不启动任何服务；加 `--connect` 时，按上面的流程确认、启动一次，再打印每个工具的名字和属性。

### 3.4 每次运行

- 用户服务和内置服务一起，在 `open_tool_registry` 里按运行启动和关闭，生命周期的约束不变（同一个 asyncio task）。
- 一个用户服务在某次运行时启动失败：跳过它，这次运行照常进行，只是看不到它的工具（第 8 节第 4 问）。发一条进度事件 `mcp_server`（服务名、`unavailable`、异常类型），命令行和网页显示一行中文。内置服务启动失败，行为不变。
- 每次调用的等待上限用配置的 `timeout_seconds`。
- 环境变量只传配置里列出的名字，值在启动服务时从进程环境里取；任何记录里都不出现值。

### 3.5 谁能用、怎么管

- **只在单一循环里用**（第 8 节第 5 问）：
  - 团队成员、调研成员的工具清单不变，看不到用户工具；
  - 只读任务照现在的规则，只看得到标了 `read` 的用户工具。
- **确认**：
  - 网页：`external` 工具照旧弹确认卡片（D-087）。
  - 命令行（第 8 节第 3 问）：配置了用户服务时，没有命中权限规则的 `external` 工具也要在终端问；不是终端时按拒绝处理。实现上就是用户服务存在时，命令行总装一个 `RuleGate`（D-094），即使没有规则文件。
  - 内置工具没有 `external` 的，所以没有用户服务时，命令行的行为不变。
- **权限规则可以直接管**：比如 `tool = "notes__create_note"`，或 `effect = "external"`；`--show-permissions` 照旧打印。
- **评测**：给子进程设 `MCP_SERVERS_FILE=''`。

### 3.6 记录

- `--show-limits` 多一行：用户服务的个数和每次调用的等待上限。
- 网页健康检查多一个 `mcp_servers`：每个服务的名字和接入的工具数，不带命令和参数。
- 进度事件 `mcp_server` 只带服务名、结果和异常类型；工具调用照旧走 `before_tool`、`after_tool`，不带参数原文。

## 4. 测试（离线）

- **解析**：
  - 每个字段的合法和不合法取值；不认识的键；服务名格式；
  - 缺少的环境变量；本项目自己的密钥名；`effects` 写了 `write`；超过 10 个服务；
  - 默认文件不存在就当没有；明确指定的文件找不到时报错。
- **名字和属性**：
  - 加前缀后调用时会去掉前缀；名字不合格的工具不接；
  - 服务自己标了 `readOnlyHint`、配置里没写 `read` 的，仍然是 `external`；
  - 起名叫 `write_file` 的第三方工具，成了 `<服务>__write_file`，属性是 `external`；
  - `tools` 清单生效；没写清单时，超过 30 个就截断。
- **非文本结果**：换成宿主说明，任务不结束。
- **确认**：
  - 终端 `y` 和其他输入；不是终端时没有 `--confirm-mcp` 就拒绝；
  - 指纹记住以后不再问；改了参数要重新问。
- **真实启动**：用 `app/agent/mcp_demo/time_server.py` 当用户服务：
  - 启动检查能列出它的工具；
  - 一次运行里模型能调用 `<服务>__<工具>`；
  - 环境变量只传列出的名字（服务看不到 `DASHSCOPE_API_KEY`）。
- **运行时失败**：一个用户服务启动失败，运行照常，有 `mcp_server` 事件，内置工具照常可用。
- **谁能用**：
  - 只读任务里看不到 `external` 用户工具，看得到 `read` 的；
  - 团队成员看不到用户工具；
  - 命令行有用户服务、没有规则文件时，`external` 工具要问，不是终端时被拒绝。
- **入口**：`--show-mcp`、`--show-mcp --connect`、健康检查字段；评测子进程的环境里 `MCP_SERVERS_FILE` 是空。
- **没有 `mcp.toml`**：`init.ps1` 通过，黄金对照文件不变。

## 5. 不做的

- 不做 stdio 以外的连接方式（HTTP、SSE）。
- 不做网页上的服务配置界面。
- 不从 `.env` 读变量值，只从进程环境读（`.env` 由 pydantic 读进设置，不会进进程环境）。
- 不给团队成员和调研成员用户工具。
- 不支持 MCP 的资源（resources）和提示（prompts），只接工具。

## 7. 风险

- **运行任意命令**：配置文件本身就是要运行的命令，所以必须确认；指纹一变就重新问；文件有错就拒绝启动，不会跳过错误的服务接着跑（D-058 的思路）。
- **第三方工具的副作用不明**：默认 `external`，算有副作用：出错、超时、取消后都不重试（D-032），网页和命令行都要确认，只读任务看不到。
- **提示注入**：工具结果照旧只是证据（系统提示第 117 行）；有副作用的调用要人确认，所以注入的内容让模型去调用 `external` 工具时，人能看到。
- **每次运行都启动一遍**：第三方服务启动慢，每个任务会多花几秒。先接受，以后再考虑常驻。

## 8. 要用户定的

1. **工具名**：推荐**加服务名前缀**（`notes__search_notes`），不会和内置工具重名，也不会被当成内置工具。另一个做法是用原名、重名就拒绝启动，但起名叫 `read_file` 的第三方工具会拿到内置工具的属性。
2. **启动确认**：推荐**启动时列出命令要求确认，按配置指纹记住结果**，配置一变就重新问；不能交互时要加 `--confirm-mcp`。另一个做法是每次启动都问，更安全但很烦。
3. **命令行确认**：推荐**配置了用户服务时，命令行对没命中规则的 `external` 工具也要问**，不是终端时拒绝。另一个做法是照现在一样不问，靠用户自己写权限规则。
4. **运行时某个服务启动失败**：推荐**跳过它，运行照常**，显示一行提示。另一个做法是整个任务失败。
5. **范围**：推荐**这次只在单一循环里用**，团队成员和调研成员不变。
6. **记录**：推荐新开 **D-095**。
